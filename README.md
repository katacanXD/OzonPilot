# OzonPilot — утилита расчёта поставок (FBO / FBS)

**OzonPilot** (`OzonPilot.exe`) — консольное приложение на Go для автоматического контроля товарных остатков и расчёта потребности в поставках на склады Ozon по гибридной модели (FBO + FBS).

Продуктовое имя — OzonPilot; в коде и репозитории модуль называется `CLIForOZON`, а конфиг хранится в `%APPDATA%\CLIForOZON\config.yaml` (путь сохранён, чтобы не потерять уже введённые ключи).

Программа собирает реальные остатки со складов Ozon (с объединением распределительных центров Москвы в кластер «Москва»), остатки собственного склада (FBS) и рассчитывает суточный спрос по реальным отгрузкам за выбранный период.

## 🚀 Быстрый запуск

> Нужен только готовый `OzonPilot.exe` без сборки из исходников? Пошаговая инструкция для новых пользователей — в [ИНСТРУКЦИЯ.md](ИНСТРУКЦИЯ.md).

### Вариант 1. Запуск из исходников (Go 1.26+)
```bash
# Стандартный расчет: запас на 25 дней по истории продаж за 28 дней
go run ./cmd/app/main.go -prodazhi 28 -postavka 25
```

### Вариант 2. Компиляция в бинарный файл

**Для Windows:**
```powershell
go build -ldflags="-s -w" -o OzonPilot.exe ./cmd/app
.\OzonPilot.exe -postavka 20
```

**Для Linux / macOS:**
```bash
go build -ldflags="-s -w" -o OzonPilot ./cmd/app
./OzonPilot -postavka 20
```

## 🔑 Авторизация

При первом запуске утилита интерактивно запросит в консоли ключи доступа к Ozon Seller API:
* `Client-Id`
* `Api-Key` *(требуются права «Администратор» или «Аналитика»)*

Ключи валидируются тестовым запросом и сохраняются локально в безопасном конфигурационном файле:
* **Windows:** `%APPDATA%\CLIForOZON\config.yaml`
* **Linux/macOS:** `~/.config/CLIForOZON/config.yaml`

Файл перезаписывается только тогда, когда ключи вводятся заново. Если он недоступен на запись (профиль только для чтения, ограниченные права, песочница), программа выводит предупреждение `Не удалось обновить файл конфигурации` и продолжает работу с уже сохраненными ключами — падать с `Ошибка авторизации Ozon` из-за этого она больше не будет.

Чтобы сбросить ключи и ввести новые, запустите с флагом:
```bash
OzonPilot.exe -reset-keys
```

## ⚙️ Параметры запуска (флаги)

| Флаг              | По умолчанию | Описание |
|:------------------| :---: | :--- |
| `-postavka`       | `25` | На сколько дней вперед рассчитать целевой запас |
| `-prodazhi`       | `28` | Глубина анализа продаж в днях (историческое окно) |
| `-clusters`       | `Москва` | Список анализируемых кластеров через запятую или `all` для всех |
| `-placement-file` | `""` | Отчет о размещении: файл API или выгрузка ЛК «Стоимость размещения по товарам» (`.xlsx`/`.csv`) |
| `-report-timeout` | `5` | Сколько минут ждать готовности отчета Ozon о стоимости размещения |
| `-file`           | `""` | Путь к локальному JSON-файлу для работы в offline-режиме (без сети) |
| `-reset-keys`     | `false` | Принудительно запросить и обновить ключи API |
| `-debug`          | `false` | Включить подробные технические логи запросов |

Значения по умолчанию для `-postavka`, `-prodazhi` и `-clusters` читаются из `config.yaml`, если он существует; флаг в командной строке всегда имеет приоритет.

## 🔌 Источники данных Ozon

| Данные | Метод API | Примечание |
|:---|:---|:---|
| Каталог товаров | `POST /v3/product/list` | Возвращает только `offer_id` и `product_id` |
| SKU и названия | `POST /v3/product/info/list` | Нужен, так как остатки запрашиваются по SKU (до 1000 за вызов) |
| Остатки FBO | `POST /v1/analytics/stocks` | Доступно к продаже по кластерам и складам (пачки по 100 SKU) |
| Остатки FBS | `POST /v4/product/info/stocks` | Собственный склад продавца (пачки по 100 `offer_id`) |
| Продажи по кластерам | `POST /v3/posting/fbo/list` | История отправлений за окно `-prodazhi` |
| Стоимость размещения | `POST /v1/report/placement/by-products/create` | Статус размещения и прошлые списания. Прогноза Ozon в этом файле нет |

Остатки FBO берутся из метода `POST /v1/analytics/stocks`. Он соответствует разделу **FBO → Управление остатками** в личном кабинете, поэтому его поле `available_stock_count` совпадает с колонкой «Доступно к продаже» на сайте Ozon. Ранее использовался устаревший метод `POST /v2/analytics/stock_on_warehouses`, который Ozon помечает как deprecated, отдает остатки без разбивки по кластерам и расходится с кабинетом — именно это было причиной заниженных остатков.

Метод `POST /v1/analytics/stocks` возвращает данные с зерном **SKU × склад** и в каждой строке содержит `cluster_name`. Поэтому остатки группируются по кластеру напрямую из ответа API, а не по списку ключевых слов. Остатки всех складов кластера, включая пункты выдачи (`ПВЗ_*`, куда попадают возвраты от покупателей), суммируются в остаток кластера.

Ozon называет московский кластер **«Москва, МО и Дальние регионы»**, тогда как в `-clusters` используется короткое имя `Москва`. Соответствие задается в `clusterAliases` (`internal/client/ozon.go`) и применяется как к данным API, так и к значениям флага, поэтому ключи всегда совпадают.

Продажи из истории отправлений распределяются по тем же кластерам через карту «склад → кластер», построенную при загрузке остатков. Это устраняет прежнее ограничение, когда продажи учитывались только по Москве, а остальные кластеры всегда получали нулевой спрос. Если склад из отправления отсутствует в карте, используется резервный матчер `isMoscowWarehouse`.

### Хранение: прошлые списания и прогноз

В отчете денежные колонки, чтобы было видно и «сколько было», и «сколько еще будет»:

* **«Списано за хранение (₽)»** — прошлое списание Ozon за последние 28 дней (то же, что в личном кабинете).
* **Прогноз** — две колонки из выгрузки ЛК: «Прогноз Ozon на 28 дн. (₽)» и «Прогноз Ozon до конца месяца (₽)».

### Откуда берется прогноз

Собственный прогноз Ozon есть только в выгрузке личного кабинета **«Стоимость размещения по товарам»** (кнопка выгрузки в ЛК). Если передать её через `-placement-file`, программа показывает цифры Ozon как есть — они совпадают с кабинетом до рубля.

Файл, который Ozon отдает через API (`POST /v1/report/placement/by-products/create`), прогноза не содержит: в нем есть только прошлые списания, количество платных экземпляров и дата окончания бесплатного размещения. В этом режиме программа считает **собственную оценку** («Оценка хранения за 30 дн. (₽)») по формуле:

1. **Тариф** (₽ за экземпляр в день) оценивается по прошлому списанию: `списано ÷ (дни периода × средний остаток за период)`.
2. **Средний остаток за период** ≈ `текущий остаток FBO + продажи за период ÷ 2`.
3. **Оценка** идет по дням: остаток уменьшается на среднесуточные продажи, дни бесплатного размещения не тарифицируются.

Это именно оценка, а не алгоритм Ozon: Ozon считает по-другому — **объём товара в литрах × тариф ₽ за литр в день × дни платного размещения**. Тариф для обычных товаров — `2,5 ₽/л/день` (с 12.09.2026), бесплатное размещение — 120/150/365 дней с даты приемки в зависимости от категории. Чтобы повторить расчет Ozon, нужны объём каждой единицы и даты приемки по каждой поставке на каждый склад — в API этих данных нет, поэтому точный прогноз берется из выгрузки ЛК.

Собственная оценка и прогноз Ozon могут расходиться в 2–4 раза: она опирается на прошлые списания и продажи, а Ozon — на литраж и сроки бесплатного размещения.

### Сколько было списано: расхождение с ЛК

В списке ЛК показываются только товары, которые размещены сейчас. В файле API есть и позиции, которые за 28 дней успели постоять на складе, а потом распродались. Поэтому сумма прошлых списаний в программе может быть больше, чем в ЛК, — в титуле отчета это выделено:

```text
списано за хранение: 32 244 ₽ (из них без остатка на FBO: 5 312 ₽)
```

Если нужна цифра «как в кабинете», передайте выгрузку ЛК через `-placement-file`: в ней таких позиций нет, и суммы совпадут.

Остаток для собственной оценки берется по **всем** складам Ozon, а не только по выбранным в `-clusters`: хранение начисляется за весь остаток. Поэтому товар с остатком в другом кластере не занижает оценку. Прогноз Ozon тоже считается по всем складам — разбивки по кластерам у него нет.

Если на складах Ozon не осталось ни одной единицы, статус размещения не показывается (`-`): размещения нет, и будущих списаний тоже.

### Надежность загрузки: лимиты, повторы и остановка при сбое

Ozon ограничивает частоту обращений к Seller API. Ограничения, которые учитывает программа:

| Ограничение | Значение | Как учтено |
|:---|:---|:---|
| Общий лимит на `Client-Id` | ~2 запроса в секунду | Пауза не менее 600 мс между любыми запросами |
| `POST /v1/analytics/stocks` | ~1 запрос в минуту | Отдельная пауза 6 секунд перед каждым вызовом |

Запросы идут строго последовательно, поэтому лимит частоты не превышается даже при большом каталоге.

Дополнительно каждый запрос повторяется при временных сбоях:

* **Повторяются** статусы `429`, `500`, `502`, `503`, `504` и сетевые ошибки — с экспоненциально растущей паузой (для `/v1/analytics/stocks` — от 4 до 45 секунд, для остальных методов — от 1.5 до 15 секунд, до 5 попыток).
* **Не повторяются** `400`, `401`, `403`, `404` — повтор не поможет, ошибка возвращается сразу.
* Не доехавшие пачки `/v1/analytics/stocks` переспрашиваются отдельным проходом.

### Отчет о стоимости размещения: ожидание и повторы

Отчет Ozon формирует асинхронно, и на большом каталоге это занимает минуты — раньше ожидание в 90 секунд обрывалось, и отчет оставался без данных о хранении. Теперь:

* ожидание готовности — **5 минут** на попытку, настраивается флагом `-report-timeout <минут>`;
* пауза между проверками статуса растет от 3 до 15 секунд, чтобы не упираться в лимит частоты;
* если Ozon вернул `failed`, задание создается заново;
* скачанный файл перекачивается до 3 раз — ссылка живет несколько минут, а недокачанный файл не разбирается;
* если не удалась вся попытка, она повторяется целиком (до 2 раз).

Если данные о размещении все-таки не получены, это **видно в отчете**: причина пишется в титул и на лист «Легенда», а не маскируется нулями. Точка отказа и полный текст ошибки при этом остаются в консоли.

**Гарантия корректного результата.** Раньше при сбое загрузки остатков программа писала предупреждение и продолжала расчет, подставляя нулевые остатки, — из-за этого все поставки оказывались завышенными. Теперь критичные данные (SKU, остатки FBO, остатки FBS, история продаж) загружаются полностью, иначе расчет **останавливается** с понятной ошибкой:

```text
level=ERROR msg="Ошибка загрузки данных из Ozon API" err="критическая ошибка загрузки остатков FBO: остатки FBO получены не для всех товаров: пропущено 37 SKU из 812 после 2 проходов: ..."
```

Неверный отчет вместо ошибки больше не создается: отчет формируется только после того, как по каждому товару получены и остатки, и продажи.

## 📊 Пример результата

```text
=============================================================================================================================
 СВОДКА ПОСТАВОК | Всего: 407 | Закончились совсем: 26 | Дефицит FBO: 246 | Пустой FBS: 94
=============================================================================================================================
АРТИКУЛ                    FBS  РАЗМЕЩЕНИЕ                 СПИСАНО (₽)  ПРОГНОЗ OZON 28 ДН (₽)  ДО КОНЦА МЕСЯЦА (₽)  Москва (ПРОДАЖИ | ОСТ / ПОСТ)     СТАТУС
-------                    ---  ----------                 -----------  -----------------------  -------------------  -----------------------------     ------
Фильтр возд. Dominar       0    Платно                     4593         1947                     3745                 9 | 40 / 0                        OK
Топл. фильтр + шланг 1м    0    Платно                     1669         2755                     2849                 25 | 100 / 0                      OK
Багажник усил. Flame сер.  2    -                          1429         0                        0                    0 | 0 / 62                        NEEDS_FBO
Втулки вилки Восход        5    Бесплатно (до 15.11.2026)  0            0                        0                    12 | 0 / 10                       NEEDS_FBO
Колодки передние Honda     12   Бесплатно                  0            0                        0                    22 | 25 / 0                       OK
=============================================================================================================================
```

### Статусы:
* **`OUT_OF_STOCK`** — критично: товара нет ни на FBO, ни на FBS при активном спросе (упущенная прибыль).
* **`NEEDS_FBO`** — на складе маркетплейса дефицит, требуется отгрузка поставки.
* **`NEEDS_FBS`** — товар закончился на домашнем складе продавца.
* **`OK`** — складских запасов достаточно.

После каждого запуска дополнительно создается Excel-файл с результатами в папке `reports` рядом с исполняемым файлом. Файл содержит настоящую Excel-таблицу с фильтрами в заголовках.

### Оформление отчета

* Титульная строка со сводкой: дата, число позиций, число товаров на платном хранении, сумма прошлых списаний (с оговоркой про позиции без остатка), прогноз будущих списаний и сколько закончилось совсем.
* Полоса групп над таблицей: над тремя колонками каждого кластера стоит его название.
* У каждого кластера своя цветовая гамма: заголовок блока и его колонки «Продажи / Остаток FBO / Поставка» залиты своим цветом, колонка «Поставка FBO» выделена акцентом, блоки разделены утолщенной границей. Гаммы идут по кругу, если кластеров больше восьми.
* Колонка «Размещение FBO» подсвечивается по статусу платного хранения: `Платно` — красный, `Бесплатно (до ДД.ММ.ГГГГ)` — жёлтый, `Бесплатно` — зелёный, `-` (нет на FBO) — серый. Суммы «Списано за хранение (₽)» и прогноза выделяются красным, если они больше нуля.
* Колонки прогноза зависят от источника: из выгрузки ЛК — две колонки Ozon, из файла API — одна колонка «Оценка хранения за 30 дн. (₽)».
* Колонка «Статус» подсвечивается по итоговой оценке товара.
* Продажи и остатки выводятся целыми числами — это штуки, поэтому в колонках «Продажи … за период (шт)», «Остаток FBO» и «Поставка FBO» нет дробной части.
* Лист «Легенда» расшифровывает все цвета.
* Если данные о размещении не загрузились, в титуле и на листе «Легенда» пишется причина (`ВНИМАНИЕ: данные о размещении Ozon не получены…`), чтобы пустые денежные колонки не читались как нулевые списания.
* При печати лист вписывается по ширине в альбомный A4. Строки и колонки не закреплены — по таблице можно прокручивать свободно.

Консольный вывод сводки сейчас отключен — результат формируется только в Excel-отчете. Чтобы вернуть таблицу в консоль, раскомментируйте вызов `printer.PrintSummaryTable` в `cmd/app/main.go`.

---

**OzonPilot — неофициальный инструмент.** Он не связан с Ozon и не является официальным продуктом Ozon. API и форматы отчётов могут меняться со стороны Ozon; используйте программу как помощника, а не как источник юридически значимых цифр.


В отчетах колонка продаж показывает фактическое количество продаж за период `-prodazhi`. Среднесуточные продажи используются только внутри расчета необходимой поставки.
