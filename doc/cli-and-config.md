# Флаги, конфиг и авторизация

## Флаги командной строки

| Флаг | Тип | По умолчанию | Что делает |
|:---|:---|:---:|:---|
| `-prodazhi` | число или `mounth`/`quarter` | `28` | Глубина истории продаж. Принимает число дней (`> 0`), `mounth` (месяц: 23.09–22.10 для 22.10) или `quarter` (квартал). Используется для запроса отправлений, для отчёта о размещении и как знаменатель при оценке тарифа хранения. |
| `-postavka` | число или `mounth`/`quarter` | `25` | На сколько дней вперёд обеспечить запас. Также принимает `mounth` и `quarter`. К значению всегда добавляется страховой запас 3 дня (см. [calculations.md](calculations.md)). |
| `-clusters` | string | `Москва` | Список кластеров через запятую. `all` — все обнаруженные кластеры. Имена нормализуются (см. [data-flow.md](data-flow.md#кластеры)). |
| `-placement-file` | string | `""` | Локальный файл отчёта о стоимости размещения: `.xlsx` или `.csv` (выгрузка ЛК или файл API). Подмена автоматического запроса к API. |
| `-report-timeout` | int | `5` | Сколько минут ждать готовности отчёта Ozon о стоимости размещения на одну попытку. Должно быть `> 0`. |
| `-file` | string | `""` | JSON с готовыми строками отчёта — offline-режим, без сети и ключей. |
| `-reset-keys` | bool | `false` | Забыть сохранённые ключи и спросить заново (только online). |
| `-debug` | bool | `false` | Уровень логирования Debug (добавляет статусы опроса отчёта). |

Порядок разрешения значений по умолчанию:

1. `config.yaml` (если файл есть и читается);
2. хардкод в `cmd/app/main.go`: `28`, `25`, `Москва`;
3. явный флаг в командной строке — всегда побеждает.

Примеры:

```powershell
.\OzonPilot.exe -postavka 30 -prodazhi 14
.\OzonPilot.exe -clusters "Москва,Санкт-Петербург,Казань" -placement-file "C:\Downloads\placement.xlsx"
.\OzonPilot.exe -clusters all -debug
.\OzonPilot.exe -report-timeout 10
.\OzonPilot.exe -reset-keys
.\OzonPilot.exe -file doc\example-offline.json -clusters "Москва"
```

## Конфигурация

### Где лежит

| ОС | Путь |
|:---|:---|
| Windows | `%APPDATA%\CLIForOZON\config.yaml` |
| Linux / macOS | `~/.config/CLIForOZON/config.yaml` |

Путь определяется через `os.UserConfigDir()`. Если системный каталог не определился, используется текущая папка. Каталог создаётся с правами `0700`, файл — `0600` (на Windows права не действуют).

### Структура

```yaml
client_id: "12345"
api_key: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
prodazhi: 28
postavka: 25
clusters: "Москва"
```

Имена ключей в конфиге совпадают с именами флагов намеренно — так конфиг и командная строка не расходятся.

### Когда файл создаётся и когда перезаписывается

- **Создаётся** при любом запуске, если файла нет: сначала с дефолтами, потом дописывается при сохранении ключей. Происходит это ещё до авторизации, поэтому файл появится и в offline-режиме.
- **Перезаписывается** в двух случаях:
  1. ключи успешно проверены Ozon (`ValidateOrPromptKeys`);
  2. значение `-clusters` отличается от сохранённого — новый список записывается в конфиг.
- **Не перезаписывается** при изменении `-prodazhi` / `-postavka`: флаги не сохраняются. Чтобы поменять значения по умолчанию, правьте файл руками.

Следствие второго пункта: запуск с `-clusters all` сохраняет в конфиг строку `all`, и следующий запуск без флага тоже будет `all`. Это поведение кода, а не ошибка чтения.

### Если файл недоступен на запись

Ключи уже прочитаны, Ozon их принял, запись не удалась (read-only профиль, чужой ACL, песочница) — программа пишет предупреждение `Не удалось обновить файл конфигурации, работаю с текущими ключами` и продолжает считать. Падение из-за этого убрано специально, тест на это — `internal/config/config_test.go`.

## Авторизация

1. Если `client_id` или `api_key` пустые — интерактивный запрос в консоли (`Enter Ozon Client-Id:`, `Enter Ozon Api-Key:`).
2. Ключи проверяются реальным запросом `POST /v3/product/list` с `limit: 1`, таймаут 10 с.
3. `200` → ключи сохраняются, работа продолжается.
4. `401` / `403` → сообщение `Invalid keys! ...`, ключи очищаются и спрашиваются заново. Всего до 3 попыток (`maxAuthAttempts`), после чего — `превышено число попыток авторизации Ozon`.
5. Любой другой статус → фатальная ошибка `unexpected API status code: N`.
6. Сетевой сбой при проверке → фатальная ошибка `network error during credential validation`.

Сброс ключей: `-reset-keys` очищает обе переменные в памяти и запускает тот же цикл ввода/проверки. В offline-режиме флаг игнорируется — конфиг и сеть не нужны.

Права ключа: нужен доступ к Seller API, обычно роль «Администратор» или «Аналитика». Остатки и отправления без этих прав не отдаются.

## Логи

Логи идут в **stderr** в текстовом формате `log/slog`:

```text
time=2026-10-18T21:39:12+03:00 level=INFO msg="Запуск в Offline режиме" file=doc\example-offline.json
time=2026-10-18T21:39:12+03:00 level=INFO msg="Excel-отчет сохранен" file=...\reports\ozon_supply_2026-10-18_21-39-12.xlsx
```

- `-debug` включает `DEBUG` (в основном статусы опроса отчёта о размещении).
- Ключи не логируются: они уходят только в заголовках запросов. При ошибке API в текст ошибки попадает тело ответа — служебное сообщение Ozon, не секреты.
- Консольная сводка-таблица (`printer.PrintSummaryTable`) реализована, но вызов в `cmd/app/main.go` закомментирован — чтобы вернуть, раскомментируйте строку.

## Коды возврата

| Код | Когда |
|:---:|:---|
| `0` | отчёт построен и сохранён |
| `1` | любая фатальная ошибка: битый конфиг (только online), ошибка авторизации, критическая ошибка загрузки данных, невозможность записать Excel, некорректные `-prodazhi`/`-postavka`/`-report-timeout` |

Тексты фатальных ошибок — в [README.md](README.md#частые-проблемы).

## Лимиты Ozon и повторы

Все запросы идут **строго последовательно**, глобальный ограничитель общий на процесс.

| Параметр | Значение | Комментарий |
|:---|:---|:---|
| Пауза между любыми запросами | 600 мс | общий лимит Ozon ~2 запроса/с на `Client-Id` |
| Пауза перед `/v1/analytics/stocks` | 6 с | у метода жёсткий лимит частоты |
| Повторы | до 5 попыток | паузы растут экспоненциально |
| Пауза обычных методов | 1,5 → 3 → 6 → 12 с (потолок 15) | `defaultRequestOpts` |
| Пауза `/v1/analytics/stocks` | 4 → 8 → 16 → 32 с (потолок 45) | `analyticsStocksOpts` |
| Повторяемые статусы | `429`, `500`, `502`, `503`, `504`, сетевые ошибки | `isRetryableStatus` |
| Неповторяемые статусы | `400`, `401`, `403`, `404` и прочие 4xx | повтор бессмысленен |
| Таймаут HTTP-клиента | 60 с | на один запрос |
| Ограничение размера ответа | 64 МБ | защита от «бесконечного» тела |
| Повторные проходы остатков FBO | 2 | недоехавшие пачки перезапрашиваются |
| Ожидание отчёта о размещении | 5 мин на попытку (`-report-timeout`), опрос 3 → 15 с | `/v1/report/info` |
| Повторы отчёта о размещении | создание — до 2 раз; вся попытка — до 2 раз; скачивание файла — до 3 раз | при `failed` задание создаётся заново |

Размеры пачек: каталог — 1000, SKU/названия — 1000, остатки FBO — 100 SKU, остатки FBS — 100 артикулов, отправления — 100 за страницу.

Практический вывод: на каталоге 800+ SKU только загрузка остатков FBO занимает порядка минуты плюс паузы; полный запуск — несколько минут. Это следствие лимитов Ozon, а не медленного кода.
