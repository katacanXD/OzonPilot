## Пакеты и ответственность

| Пакет | Файлы | Ответственность |
|:---|:---|:---|
| `cmd/app` | `main.go` | флаги, уровень логов, выбор online/offline, привязка отчёта о размещении, запуск экспорта |
| `internal/config` | `config.go` | Viper: создание/чтение `config.yaml`, запрос и проверка ключей |
| `internal/client` | `ozon.go` | HTTP-клиент Ozon, троттлинг, повторы, разбор ответов, отчёт о размещении (API и файл) |
| `internal/domain` | `model.go`, `calculator.go`, `storage.go` | модель данных, расчёт поставки и статуса, прогноз хранения |
| `internal/printer` | `excel.go`, `table.go` | Excel-отчёт и (отключённая) консольная таблица |

Зависимости односторонние: `domain` не знает ни про CLI, ни про HTTP; `client` знает про `domain`, но не наоборот.

## Online: источники данных Ozon

Все запросы — `POST` с заголовками `Client-Id`, `Api-Key`, `Content-Type: application/json`. Базовый URL — `https://api-seller.ozon.ru`.

| Шаг | Метод | Что берём | Пачка | Критичность |
|:---|:---|:---|:---:|:---|
| 1 | `/v3/product/list` | `offer_id`, `product_id` (постранично по `last_id`) | 1000 | критично |
| 2 | `/v3/product/info/list` | `sku` и `name` по `offer_id` | 1000 | критично |
| 3 | `/v1/analytics/stocks` | `available_stock_count` по `sku` × склад + `cluster_name` | 100 SKU | критично (fail-fast) |
| 4 | `/v4/product/info/stocks` | FBS: `present` для `type == "fbs"` | 100 артикулов | критично |
| 5 | `/v3/posting/fbo/list` | отправления FBO за окно `-prodazhi` | 100 (курсор) | критично |
| 6 | `/v1/report/placement/by-products/create` + `/v1/report/info` | отчёт о стоимости размещения | — | не критично (warn) |

Почему именно так:

- `/v3/product/list` не отдаёт SKU, а остатки запрашиваются только по SKU — отсюда шаг 2.
- `/v1/analytics/stocks` — тот же источник, что раздел **FBO → Управление остатками** в кабинете, поэтому `available_stock_count` совпадает с колонкой «Доступно к продаже». Устаревший `/v2/analytics/stock_on_warehouses` не используется: он без кластеров и занижает остатки.
- FBS берётся из `/v4/product/info/stocks`: суммируются только записи с `type == "fbs"`.

### Дубли и защита от неполных данных

- Пагинация каталога и отправлений останавливается, если курсор/`last_id` пуст или повторяется.
- `loadFBOStocks` возвращает `(склад → кластер, покрытые SKU, ошибка)`. Недоехавшие пачки перезапрашиваются отдельным проходом (всего 2 прохода). Если пачки остались — **ошибка**, а не «нулевые остатки».
- После загрузки идёт проверка: у каждого товара с непустым SKU должны быть данные по остаткам. Иначе — ошибка `остатки FBO не получены для N товаров … расчет остановлен`.
- Сбой FBS хотя бы по одному пакету — тоже фатальная ошибка.
- Сбой истории отправлений — фатальная ошибка.

Логика простая: **неполные данные → нет отчёта**. Раньше при сбое подставлялись нулевые остатки, и все поставки оказывались завышенными.

## Кластеры

Ozon называет московский кластер «Москва, МО и Дальние регионы», а в флагах и конфиге используется короткое `Москва`. Соответствие задаёт `clusterAliases` в `internal/client/ozon.go` и применяется к обеим сторонам: и к данным API, и к значениям `-clusters`, поэтому ключи всегда совпадают.

| Ozon / пользователь | Результат |
|:---|:---|
| `Москва, МО и Дальние регионы`, `москва` | `Москва` |
| `Санкт-Петербург и СЗО`, `Санкт-Петербург`, `СПб`, `Питер` | `Санкт-Петербург` |
| `Поволжье`, `Казань`, `Самара` | `Поволжье` |
| `Юг`, `Ростов-на-Дону`, `Ростов`, `Краснодар` | `Юг` |
| `Урал`, `Екатеринбург` | `Урал` |
| `Сибирь`, `Новосибирск` | `Сибирь` |
| `Дальний Восток`, `Хабаровск`, `Владивосток` | `Дальний Восток` |
| `Воронеж`, `Калининград`, `Северный Кавказ`, `Беларусь`, `Казахстан` | без изменений |
| любое незнакомое имя | без изменений |

### Карта «склад → кластер»

`/v1/analytics/stocks` отдаёт по строке на пару SKU × склад, и в каждой строке есть `cluster_name`. Из этих строк строится карта `склад → кластер`; ключ склада нормализуется в верхний регистр, потому что разные методы Ozon отдают регистр по-разному (`Новосибирск_РФЦ_НОВЫЙ` / `НОВОСИБИРСК_РФЦ_НОВЫЙ`).

Эта же карта переиспользуется при разборе отправлений — склады из истории продаж попадают в те же кластеры, что и остатки. Единый источник истины, никакого повторного угадывания по названиям.

Если склада в карте нет, работает резервный матчер:

- Москва и МО — по списку ключевых слов (`вешки`, `ватутинки`, `домодедово`, `пушкино`, `софьино`, `хоругвино`, `москва` и др.);
- дальше по городам: `петербург`/`шушары`/`бугры` → Санкт-Петербург, `казань`/`самара` → Поволжье, `ростов`/`краснодар`/`невинномысск`/`адыгея` → Юг, `екатеринбург`/`пермь` → Урал, `новосибирск`/`красноярск` → Сибирь, `хабаровск`/`владивосток` → Дальний Восток.

### Что попадает в карты остатков и продаж

Для каждого товара ведутся:

- `FBOClusters` — остаток по нормализованному кластеру **и** по названию склада, если оно отличается от кластера. Поэтому `-clusters "ХОРУГВИНО_РФЦ"` тоже сработает: это просто ещё один ключ.
- `PeriodSales` — продажи за окно по тем же ключам (склад + кластер).
- `ClusterSales` — `PeriodSales` / `-prodazhi`, среднесуточные продажи; используются только в расчёте.
- `TotalFBO` — остаток по всем складам, **без двойного счёта**: одна строка ответа API = одно прибавление.
- `TotalPeriodSales` — суммарные продажи по всем складам, тоже один раз на позицию отправления.

`-clusters all` подставляет не имена складов, а список уникальных кластеров из карты, отсортированный по алфавиту.

## Продажи: как считается спрос

Окно: `[сейчас − prodazhi дней; сейчас]` в UTC, формат `2006-01-02T15:04:05Z`.

- Отправления со статусом `cancelled` пропускаются.
- Каждая позиция отправления (`offer_id`, при отсутствии — `sku`) увеличивает счётчики склада и кластера.
- Если склад не удалось отнести к кластеру, продажи попадут в `TotalPeriodSales`, но не в конкретный кластер — в лог уйдут счётчики `всего_fbo_заказов` и `с_определенным_кластером`, по их разнице это видно.
- Возвраты, невыкупы и отмены по инициативе покупателя отдельно не вычитаются: считается количество в отправлении.

## Offline-режим (флаг `-file`)

Файл — JSON-массив объектов `domain.ProductSupplyRow`. Тегов JSON у структуры нет, поэтому имена полей — **как в Go**, с точным регистром:

```json
[
  {
    "OfferID": "TEST-1",
    "Name": "Товар",
    "TotalSales": 40,
    "CurrentFBS": 5,
    "ClusterData": {
      "Москва": { "PeriodSales": 30, "DailySales": 1.07, "StockFBO": 10, "Supply": 45 }
    },
    "TotalSupply": 45,
    "OverallStatus": "NEEDS_FBO",
    "Priority": 2,
    "PlacementInfo": "Платно",
    "TotalFBOStock": 10,
    "TotalPeriodSales": 40,
    "StorageCost": 1200,
    "StorageForecast": 900.5,
    "OzonStorageForecast28": 0,
    "OzonStorageForecastMonth": 0,
    "HasOzonStorageForecast": false
  }
]
```

Что программа делает с этим файлом:

| Поле | Поведение |
|:---|:---|
| `ClusterData` ключи | нормализуются по алиасам кластеров |
| `PeriodSales` | если `0`, а `DailySales != 0` — досчитывается как `DailySales × -prodazhi` |
| `TotalFBOStock`, `TotalPeriodSales` | если **оба** нулевые — считаются суммой по кластерам |
| `Supply`, `OverallStatus`, `Priority` | **не пересчитываются**, используются как есть (влияют на сортировку и цвета) |
| `PlacementInfo`, `StorageCost`, прогнозы | берутся из JSON; данные о размещении дополнительно подтягиваются из `-placement-file` по `OfferID` |

Полезный пример — `example-offline.json` рядом с этим файлом. Запуск:

```powershell
.\OzonPilot.exe -file doc\example-offline.json -clusters "Москва,Санкт-Петербург"
```

Offline-режим не читает ключи и не ходит в сеть; битый конфиг ему не мешает. Отчёт создаётся в `reports` рядом с exe.

## Отчёт о стоимости размещения

Два источника, приоритет у файла:

1. `-placement-file` — `.xlsx` или `.csv`. Подходит и выгрузка ЛК «Стоимость размещения по товарам», и файл, скачанный из API.
2. Если файла нет — API: `POST /v1/report/placement/by-products/create` с периодом `[сегодня − prodazhi; сегодня]`, затем опрос `/v1/report/info` (пауза растёт от 3 до 15 секунд, ожидание 5 минут на попытку — меняется флагом `-report-timeout`), скачивание по `file` (только `http`/`https`) и разбор.
3. Если API-отчёт не получился — **предупреждение** в лог, отчёт строится с пустыми денежными колонками и предупреждением в титуле и на листе «Легенда».

Механика устойчивости:

- создание задания повторяется до 2 раз, при статусе `failed` задание создаётся заново;
- скачивание файла перекачивается до 3 раз: ссылка живёт несколько минут, а недокачанный файл не разбирается;
- если не удалась вся попытка (таймаут, ошибка генерации), она повторяется целиком — до 2 раз;
- ошибки `/v1/report/info` в процессе ожидания не прерывают опрос: файл продолжает формироваться.

### Разбор файла

Формат определяется содержимым: сначала пробуем Excel, если не вышло — CSV (разделитель `;`, `,` или таб, BOM срезается).

Строка заголовков ищется в первых 5 строках по словам `артикул` / `offer_id` / `offer`. Если следующая строка — подзаголовки (в ней ≥2 слов вроде «списано», «остаток», «прогноз», «шт», «дней»), заголовок считается двухстрочным — так устроена выгрузка ЛК.

Колонки распознаются по ключевым словам:

| Поле | Признак в заголовке |
|:---|:---|
| артикул | `артикул`, `offer_id`, `offer` |
| SKU | `sku`, `product_id` |
| статус | `статус` |
| дата окончания бесплатного размещения | `дата` + `бесплат`/`окончан`/`начал`/`срок`, либо `бесплатно до` / `окончание бесплатного` / `срок бесплатного` |
| списано (₽) | `списан`, `стоимост`, `начислен`, `плата` |
| платных экземпляров | `платных` |
| всего экземпляров | `экземпляр`, `кол-во` |
| остаток на складах, шт | `остаток на складах` + `шт` |
| размещение без платы, шт | `размещение без платы` + `шт` |
| вынужденное размещение, шт | `вынужденное размещение` + `шт` |
| прогноз на 28 дней | `прогноз` + `28` |
| прогноз до конца месяца | `прогноз` + `месяц` |

Строки с одинаковым артикулом (разные склады) суммируются: деньги, количества, прогнозы. Статус размещения выводится по правилам:

1. есть колонки количеств → `Платно`, если платных экземпляров или денег больше нуля; `Бесплатно`, если есть экземпляры; иначе `-`;
2. есть колонка остатка → `-` при нуле, `Платно` при вынужденном размещении или прогнозе > 0, `Бесплатно (до ДД.ММ.ГГГГ)` при дате в будущем, иначе `Бесплатно`;
3. иначе — по тексту статуса/даты из файла, при отсутствии — по сумме списаний.

Даты принимаются в форматах `ГГГГ-ММ-ДД` и `ДД.ММ.ГГГГ` (время отрезается). Прочерк, пусто и `null` означают «даты нет».

Результат индексируется **дважды** — по артикулу и по SKU, чтобы привязка работала, даже если один из идентификаторов в отчёте пуст. В online-режиме поиск идёт сначала по `OfferID`, потом по SKU; в offline — только по `OfferID`.

Если у товара нулевой остаток на всех складах Ozon, статус размещения очищается (`-`): размещения нет, будущих списаний тоже. Денежные суммы при этом сохраняются — они про прошлое.

## Что происходит при сбоях

| Сбой | Поведение |
|:---|:---|
| Сбой запроса SKU и названий (`/v3/product/info/list`) | фатально (без SKU нельзя запросить остатки) |
| Ozon не вернул SKU для части товаров | не фатально, но такой товар получит остаток 0 — см. [known-issues.md](known-issues.md#2-товары-без-sku-выглядят-как-дефицит) |
| Остатки FBO неполные | фатально, с перечислением пропущенных артикулов |
| Остатки FBS неполные | фатально |
| История отправлений не загрузилась | фатально |
| Отчёт о размещении не сформировался | предупреждение: отчёт без денежных колонок, предупреждение в титуле и на листе «Легенда» |
| Нет прав на запись в `reports` | фатально |
| `4xx` кроме 429 | сразу ошибка, без повторов |
| `429` / `5xx` / сеть | до 5 попыток с растущей паузой |
